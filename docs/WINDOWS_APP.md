# Windows 앱 · 0.6.1 프리릴리스

[v0.6.1 설치 파일·SHA-256·검증 기록](https://github.com/ParkYaeseong/llm-tuning-factory/releases/tag/v0.6.1)

## 소스 업데이트: ENG / KOR 언어 선택

현재 소스에는 오른쪽 위 **ENG / KOR** 선택기가 있습니다. 초기값은 KOR이며, 선택은 이 PC의
`factory.language` 설정으로 저장해 다시 열어도 유지합니다. 메뉴·양식·실행 안내·튜토리얼을 즉시
바꾸며 입력 중인 프로젝트·연결 값과 검토한 계획은 유지합니다. 언어 변경 자체로 연결 정보를 저장하거나
실행을 제출하지 않습니다. 프로젝트명·데이터·모델 ID·원본 진단·학습 로그는 원문을 유지합니다.
이 항목은 소스 기능 설명이며 기존에 배포·설치한 빌드에 자동 적용되는 업데이트가 아닙니다.

아래 안내는 기존 0.4.0 설치 기준을 포함합니다.

Windows x64 설치형 앱입니다. 사용자 PC에 Python, Rust, Git, GPU 드라이버를 따로 설치할 필요가
없도록 Python 실행 엔진을 설치 파일에 포함합니다. 학습용 CUDA와 LLaMA-Factory는 RunPod 또는 GPU 서버에 설치합니다.
WebView2가 없으면 설치 중 Microsoft 런타임 다운로드가 필요합니다.
현재 설치 파일은 코드 서명하지 않은 내부 검토용입니다. Windows SmartScreen이 경고하면 배포 페이지의 SHA256을
확인한 뒤 ‘추가 정보’ → ‘실행’을 누릅니다.

**0.4.0에서 달라진 점.** 왼쪽 메뉴에 **프로젝트**, **레시피**, **그래프 실행**(워크스페이스)과 **실행 프로필**(설정)이
생겼습니다. 목적과 데이터를 직접 정한 빈 프로젝트에서 CSV·JSON·JSONL을 열 연결해 가져오고, 여러 학습·평가·자동 선택·병합
단계를 카드로 직렬·병렬 연결한 학습 그래프를 계획·승인한 뒤 백그라운드 컨트롤러로 실행합니다. 0.3.0의 GPU 서버(SSH 직접 실행)와
MLflow “인증 없음”도 이번 설치 파일에 들어 있습니다. 기존 화면(**학습 설정**, **실행 관리** 등)은 **단일 학습** 메뉴에서
그대로 쓸 수 있습니다. 처음부터 끝까지의 순서는 [학습 프로젝트·그래프 안내](TRAINING_WORKFLOWS.md)에 있습니다.

## 처음 사용

처음이라면 작업 공간의 **튜토리얼 시작**(처음 사용 카드), 왼쪽 메뉴의 **튜토리얼** 또는 Ctrl+K의 **튜토리얼**로
약 7분, 16단계의 안내를 시작하세요. 화면을 막지 않는 말풍선과 강조 표시를 따라 하며, 튜토리얼 중에 **튜토리얼**을
다시 누르면 처음부터 다시 시작합니다. 5~8단계에서 앱에 포함된 합성 예제 `tutorial_sample`(8건)을 양식에 채워 미리보기·등록하고,
학습 설정에서 선택해 실행 계획(dry-run)까지 직접 확인합니다. 11~15단계는 프로젝트·실행 프로필·데이터 가져오기·학습 그래프·
그래프 실행 화면을 설명만 하며 아무것도 만들거나 저장하지 않습니다. 연결 정보는 필요하지 않습니다. 연결 단계는 RunPod와 GPU 서버(BOP 등)
방식을 설명만 하며 입력을 요구하지 않습니다. RunPod·GPU 서버에 연결하거나 데이터를 전송하거나 자격 증명·프로필을 저장하지 않으며
GPU 비용도 없습니다. **Esc** 또는 **그만하기**로 언제든 끝낼 수 있습니다. 진행 중인 요청이 있으면 끝나는 것을 기다린 뒤
종료합니다. 끝나면 튜토리얼 전의 학습 설정 초안·실행 계획·데이터 양식·미리보기를 되돌려 놓습니다. 완료 또는 종료 사실은
이 PC에 기억되어 처음 사용 카드가 다시 나타나지 않으며, 이후에도 언제든 다시 시작할 수 있습니다.
등록한 `tutorial_sample`은 계속 남으며 합성 표시와 GPU 전송 차단이 적용되어 실제 학습에는 쓸 수 없습니다.
이 ID는 예약되어 대소문자·끝 점 변형과 S3 가져오기도 거부되고, ‘시작하기’ 목록의 데이터 단계에도 포함되지 않습니다.

아래는 기존 **단일 학습** 화면(연결 설정 → 학습 설정 → 실행 관리)의 순서입니다. 학습 그래프는
[학습 프로젝트·그래프 안내](TRAINING_WORKFLOWS.md)를 따르며, RunPod Pod와 GPU 서버를 **실행 프로필**로 따로 등록합니다.

1. 제공받은 `LLM.Tuning.Factory_0.4.0_x64-setup.exe`(배포 페이지의 설치 파일)를 설치합니다. 이전 버전에서 업데이트한다면 먼저 아래
   ‘업데이트·제거’를 확인하세요.
2. **연결 설정**에서 RunPod API 키, 배정받은 Pod ID, SSH 개인키 파일과 서버 지문을 입력합니다.
   SSH 지문은 관리자가 신뢰할 수 있는 경로로 확인해 전달해야 합니다. 접속 시 관측한 값을 자동 승인하지 않습니다.
3. MLflow 주소와 OIDC 인증값 또는 별도 토큰을 입력하고 **연결 정보 저장**, **연결 검사**를 누릅니다.
   기존 공용 주소가 기본값입니다. 인증값은 Windows 자격 증명 저장소에 저장되며 화면에 다시 반환하지 않습니다.
   .env를 직접 편집할 필요가 없습니다. SSH 개인키는 원래 파일 위치에 남습니다.
4. RunPod에서 **본인에게 배정된 Pod**를 시작합니다. /workspace에 Network Volume이 연결되고
   public TCP SSH가 제공되어야 합니다. 앱은 Pod를 자동 생성·시작·정지·삭제하지 않습니다.
5. **학습 환경 준비**를 확인 후 실행합니다. 실행 중인 Pod에 앱 전용 Python 3.12 환경과 해시로 고정한
   의존성, 현재 앱과 일치하는 작업 패키지를 설치합니다. 최초 설치는 수 분 이상 걸릴 수 있으며
   GPU 요금과 저장·전송 비용이 발생할 수 있습니다. Python3/pip/flock, C 컴파일러(cc/gcc) 및 외부 패키지 다운로드가
   가능한 Pod가 필요합니다. 시스템 Python이나 기존 다른 학습 환경을 변경하지 않습니다.
   CUDA devel 계열 이미지를 권장합니다. CUDA가 보여도 C 컴파일러가 없으면 Triton 학습 초기화가
   실패하므로 앱이 준비 단계에서 차단합니다. 컴파일러 설치는 Pod 관리자가 수행합니다.
6. **GPU 정보 → 학습 설정에 적용**으로 실제 GPU 종류·수·현재 요금을 가져옵니다.

기존 Pod를 시작할 때 `There are not enough free GPUs on the host machine` 오류가 나면 해당 호스트의
GPU가 부족한 상태입니다. 앱을 다시 설치해도 해결되지 않습니다. 관리자가 같은 데이터센터의 가용 GPU와
저장 볼륨을 확인해 별도 Pod를 준비한 뒤 새 Pod ID와 검증된 SSH 지문을 입력합니다. 기존 작업의 결과
회수는 원래 실행한 Pod ID를 확인하므로, 연결을 바꾸는 것만으로 다른 Pod에서 이어받지는 않습니다.

### GPU 서버(SSH 직접 실행)로 연결하기

RunPod 대신 BOP 같은 기관 Linux GPU 서버를 쓰는 경우 2번과 4~6번 대신 아래 순서를 따릅니다.
RunPod API 키, Pod ID, /workspace 네트워크 볼륨은 필요하지 않습니다. 앱은 서버를 켜거나 끄지 않습니다.

1. 관리자에게 받을 정보: 서버 주소와 SSH 포트, 접속 계정, 관리자가 신뢰할 수 있는 경로로 확인한 서버
   **SHA256 지문**(ED25519 호스트 키 지문을 요청하세요), 내가 쓸 수 있는 GPU, 쓰기 가능한 작업 폴더(절대 경로,
   예: /home/USER/factory). SSH 키 쌍은 직접 만들고 공개키 등록을 관리자에게 요청합니다. 개인키는 절대 전달받거나
   보내지 않습니다. 개인키는 OpenSSH 형식의 암호(passphrase) 없는 파일이어야 하며 SSH 에이전트는 사용하지 않습니다.
   PuTTY .ppk 경로는 저장 시 거부되므로 OpenSSH 형식으로 변환하세요. 접속 시 관측한 지문은 자동으로 신뢰하지 않습니다.
   root 계정은 필요하지 않습니다. 작업 폴더 경로에는 영문자·숫자와 `_ . / -`만 쓸 수 있습니다(한글 불가).
2. **연결 설정**의 **GPU 연결 대상**에서 “GPU 서버 · SSH 직접 실행 (BOP 등)”을 고릅니다.
   **서버 주소**, **SSH 포트**, **접속 계정**, **SSH 개인키 파일**(**파일 찾기**로 선택, 키 내용은 붙여 넣지 않음),
   **SSH 서버 지문**, **작업 폴더 · 절대 경로**, **시간당 비용 (USD) · 서버 전체**를 입력하고 저장합니다.
   비용은 직접 입력하는 값이며 클라우드 요금 조회 결과가 아닙니다. 내부 서버는 0을 입력할 수 있습니다.
3. **GPU 학습 환경** 카드의 **GPU 목록 조회**로 서버의 NVIDIA GPU를 읽고, 사용할 GPU를 **정확히 1개** 체크한 뒤
   **GPU 선택 저장**을 누릅니다. 현재 앱은 작업당 GPU 1개만 허용하며 더 많이 저장하면 거부됩니다. 이미 저장된 선택이
   1개를 넘으면 환경 확인·준비 등 서버 동작이 비활성화되고 설정 단계가 완료되지 않은 것으로 표시되며,
   **데이터 전송에 동의하고 학습 시작**도 비활성화되고 정책 안내 메시지가 표시됩니다. GPU는 번호가 아닌 UUID로 저장됩니다. 조회만으로는 파일을 만들거나 설치하지 않습니다.
4. **환경 확인**은 작업 폴더의 학습 환경이 현재 앱과 맞는지 읽기 전용으로 확인합니다.
   **학습 환경 준비**는 승인 창에서 서버·작업 폴더·선택 GPU를 확인한 뒤 실행합니다. 작업 폴더 아래에
   앱 전용 Python 환경, 캐시를 만들며 데이터는 전송하지 않습니다. sudo·apt를 사용하지 않으며 서버 기본 Python을 바꾸지 않습니다.
   다른 사용자 환경도 변경하지 않습니다. 준비에는 서버에서 PyPI 또는 설정된 pip/uv 미러에 접속할 수 있어야 합니다
   (Python 3.12는 없을 때만 내려받습니다). Hugging Face 모델 다운로드만 작업 폴더의 hf-cache를 미리 채워 피할 수 있습니다. 최초 준비는 다운로드 때문에 시간이 걸립니다.
5. 학습 설정으로 이동하기 전에 **GPU 정보 → 학습 설정에 적용**을 눌러 선택한 GPU 종류·수와 입력한 시간당 비용을 반영합니다.
6. **실행 계획 확인**의 목적지 줄(‘GPU 서버: 주소 · 선택 GPU n개 · GPU: 종류’)이 의도한 서버인지 확인합니다.
   서버 설정이 불완전하거나 올바르지 않거나 GPU 선택이 없어 계획에 목적지 해시가 없으면 시작 버튼이 비활성화되고
   사유가 표시됩니다. 설정을 바꿔 저장하면 기존 계획이 사라지므로 계획을 다시 확인합니다. 계획 이후 바뀐 설정으로
   제출하면 “연결 설정이 실행 계획 이후 바뀌었습니다. 실행 계획을 다시 확인하세요.”라며 거부됩니다.
   **실행 관리**의 **실행 위치** 열에서 작업별 목적지(‘GPU 서버 · 주소’ 또는 “RunPod”)를 볼 수 있습니다.

서버 요구 조건: Linux, 접속 계정이 읽을 수 있는 /etc/machine-id, nvidia-smi로 보이는 NVIDIA GPU(MIG 분할은 거부하며 MIG GPU가 하나라도 있으면 조회 전체가 실패),
pip가 있는 python3, flock, C 컴파일러(cc). 작업 폴더는 쓰기 가능해야 하며 경로와 상위 폴더(예: /home)가 심볼릭 링크이면 안 되므로 실제(resolved) 경로를 입력합니다.
없는 도구는 설치하지 않고 관리자에게 요청하라는 메시지를 표시합니다.

**환경 준비 예약.** 준비 중 연결이 끊기는 등 종료를 확인하지 못하면 예약이 남아 같은 서버의 준비·학습을 막습니다.
**준비 예약 확인**으로 목록을 보고, ‘종료 확인 필요’ 항목과 앱이 강제 종료되어 ‘준비 중’으로 남은 항목은
**원격 준비 종료 확인 · 예약 해제**로 해제합니다. ‘준비 중’ 항목은 실제로 아직 실행 중일 수 있으므로 강한 경고가 표시됩니다.
해제 전에 서버에서 준비 프로세스가 끝났는지 직접 확인해야 하며 승인 창에서 이를 확인합니다. 저장된 서버 설정과
다른 서버로 만든 예약은 그 설정으로 바꾼 뒤 해제합니다.

학습 단계와 S3 연결의 상세 절차는 [학습·스토리지 안내](TRAINING_AND_STORAGE.md)를 확인하세요.

### MLflow 인증 없음

로컬이나 내부망의 인증 없는 MLflow 서버는 **MLflow 서버 주소**에 주소(예: `http://127.0.0.1:5000`)를 넣고
**인증 방식**에서 “인증 없음 · 로컬·내부 서버”를 고릅니다. OIDC·토큰 입력란이 숨겨지며 앱은 저장된 인증값을
지우지 않고 사용하지도 않습니다. 다른 방식으로 되돌리면 저장된 값을 다시 씁니다. 토큰이나 OIDC 인증값(주소와 시크릿 모두 있을 때)을
쓰면 데스크톱 앱과 CLI 모두 HTTPS 주소만 허용하고 HTTP는 인증 없음에서만 허용됩니다. HTTP 산출물 위치(서버가 실행별로 정한 위치 포함)도 거부됩니다. OIDC 주소만 있고 시크릿이 없으면 앱은 시작되지만 MLflow 동작이 아래 오류로 실패합니다. 인증값이 있으면 로컬 `file:`·`sqlite:` 저장소 주소도 거부되므로 로컬 저장소는 인증값을 비우고 사용하세요. **인증 없음은 서버에 접근할 수 있는 누구나
실행 기록을 볼 수 있으므로 신뢰할 수 있는 로컬·내부망에서만 사용하세요.** 로컬 서버 실행 예는
[운영 안내](OPERATIONS.md)를 확인하세요. **연결 검사 결과**의 MLflow 조회 줄은 ‘확인됨 · 인증 없음’처럼 방식과 함께 표시되며,
GPU 서버 연결에서는 “GPU 서버” 줄에 주소와 GPU 요약, “실제 GPU 학습” 줄에 아직 확인하지 않았음이 표시됩니다.
OIDC를 선택했는데 클라이언트 인증값이 없으면 “OIDC 인증을 선택했지만 클라이언트 인증값이 없습니다. 인증값을 입력하거나 토큰·OIDC 값을 비우세요(앱에서는 ‘인증 없음’ 선택).”라는 오류가 표시됩니다. 제출·실행 전에도 같은 점검을 합니다.

## 프로젝트와 데이터 가져오기

- **프로젝트**: 작업 공간의 “빈 프로젝트 만들기”나 **프로젝트** 화면에서 이름(필수)·작업 유형·목적만으로 만듭니다. 예제는 필요하지
  않습니다. 프로젝트 화면에서 목적, 기본 실행 프로필, 데이터 연결을 정하고 **저장**해야 반영됩니다. 다른 곳에서 먼저 저장했다면
  “최신 버전 불러오기” 또는 “내 변경으로 덮어쓰기”를 고릅니다.
- **데이터 가져오기**: 프로젝트의 “CSV·JSON 가져오기” 또는 데이터 화면의 “열 연결해 가져오기”에서 CSV·JSON·JSONL(32 MiB 이하,
  이 PC의 로컬 파일)을 가져옵니다. CSV는 “CP949 · Windows 한글” 인코딩을 고를 수 있습니다. 열을 학습 항목에 연결하고 미리보기에서
  ‘N행’ 단위의 문제를 고친 뒤 데이터 ID·버전으로 등록합니다. 등록한 버전은 바뀌지 않습니다. 이어서 학습·검증·시험으로 나누고
  (기본 80/10/10, 시드 42) “프로젝트에 연결”한 뒤 프로젝트를 저장합니다.
- ShareGPT 대화 파일은 기존 **데이터** 화면의 JSON 등록을 쓰며, 새 화면에서 나눌 수 없습니다.

## 레시피

**레시피** 화면에서 학습 단계·방법·옵션만 담은 레시피를 만들거나(“새 레시피”, “예제에서 만들기”) 복제합니다. 데이터, 기반 모델,
GPU·Pod, 승인은 들어가지 않습니다. 저장할 때마다 새 버전이 생기며 그래프의 카드는 고른 버전을 고정해 씁니다.

## 학습 그래프

프로젝트 화면의 “학습 그래프”에서 카드로 단계를 잇습니다. 빈 그래프에서는 시작 모양 네 가지(“단일 학습”, “직렬 추가 학습”,
“병렬 비교”, “병렬 비교 후 병합”)를 고를 수 있습니다. “다음 단계 추가”는 직렬, “나란히 추가”는 병렬로 카드를 더하며, 이어 붙일 수
없는 종류는 이유와 함께 꺼져 있습니다. 카드는 최대 64개, 연결은 최대 256개입니다.

- **기반 모델** 칸에서 Hugging Face 모델 버전을 고정하고 “설정·토크나이저 받기”와 “모듈 구조 확인”을 각각 안내 창에서 승인합니다.
  설정·토크나이저 파일과 safetensors 머리글만 받으며 **모델 가중치는 받지 않습니다.**
- 병합은 실제로 끝난 LoRA·QLoRA 결과만 합칩니다. 모의 실행 계획에서는 병합 단계에서 멈춥니다.
- “저장”하면 저장한 버전을 바로 검사합니다. 계획과 실행은 저장한 버전으로만 합니다.

## 계획과 승인

그래프 화면 아래 “계획과 승인”에서 계획을 만듭니다. 기본은 “모의 실행 계획 · 기본”으로 GPU를 쓰지 않고 데이터를 보내지 않습니다.
“실제 실행 계획”은 1시간 이내에 자원을 확인한 실행 프로필과 MLflow 서버 주소가 필요합니다. 실제 실행의 승인 창에서는
‘실행 승인’과 ‘데이터 전송 승인’을 각각 체크해야 등록됩니다. 최대 추정 비용은 재시도를 포함한 추정치이며 제공자의 청구 상한이
아닙니다. 같은 계획은 다시 등록하지 않으며, 등록해도 컨트롤러는 자동으로 시작하지 않습니다. 다시 실행하려면 입력을 바꿔 새 계획을
만듭니다(실행 프로필의 “자원 확인”을 다시 해도 됩니다).

## 실행 프로필과 백그라운드 컨트롤러

- **실행 프로필**(설정)에 실제 실행에 쓸 RunPod Pod와 GPU 서버를 이름 붙여 저장합니다. 연결 설정의 단일 학습 연결과 따로 보관합니다.
  SSH 개인키는 이 PC의 전체 경로(예: `C:\Users\이름\.ssh\id_ed25519`)로 입력합니다. RunPod API 키는 프로필마다 Windows 자격 증명
  저장소에 보관합니다. GPU 서버는 “GPU 목록 확인”으로 GPU를 고르고, “자원 확인”으로 GPU와 요금을 기록합니다(읽기 전용).
- 연결 설정의 “저장된 인증값 삭제”는 모든 실행 프로필의 RunPod API 키도 함께 지웁니다.
- 실제 장비 하나는 실행 프로필 하나로만 등록합니다. 같은 장비를 RunPod 프로필과 GPU 서버 프로필로 함께 등록하면 서로 다른 실행
  대상으로 계산하므로, 다른 상태 폴더나 다른 PC에서 함께 쓰면 동시 사용을 막지 못합니다.
- 컨트롤러 막대(실행 프로필·그래프 실행 화면)의 “컨트롤러 시작”으로 백그라운드 컨트롤러를 켭니다. 앱은 자동으로 켜지 않습니다.
  앱 창을 닫아도 계속 돌며, 다시 열면 “동작 중”으로 보입니다. PC가 절전·종료되면 멈추므로 “연결 끊김”이 보이면 다시 시작합니다.
- “컨트롤러 정지”는 진행 중인 단계가 끝날 때까지 기다린 뒤 멈추므로 학습 중이면 몇 시간이 걸릴 수 있습니다. 상태가 “정지”가 되면
  끝난 것입니다.
- 실행 프로필을 고치거나 RunPod 키·MLflow 인증값을 저장·변경한 뒤에는 컨트롤러를 다시 시작해야 새 값을 씁니다
  (일시정지 → 진행 중 단계 완료 대기 또는 컨트롤러 정지 → 설정 저장 → 컨트롤러 시작). 키만 바꾼 경우는 막대가 알려 주지 않습니다.
- 앱 데이터 폴더가 네트워크 경로(리디렉션된 AppData)에 있으면 컨트롤러를 시작할 수 없습니다. 단일 학습 기능은 계속 쓸 수 있습니다.

## 그래프 실행

**그래프 실행** 화면에서 실행 목록, 단계별 상태·시도·실행 위치·대기 이유·MLflow 기록과 결과를 봅니다. “일시정지”, “다시 진행”,
“취소”와 실패한 기록의 “기록 다시 시도”를 할 수 있습니다.

- “결과 대기”는 원격 결과가 늦게 올 수 있어 시간 제한이 지나기 전까지 다시 실행하지 않고 기다리는 상태입니다. 할 일은 없습니다.
- “운영자 확인 필요”는 원격 실행이 멈췄는지 앱이 알 수 없는 상태입니다. RunPod 콘솔이나 서버에서 그 작업·시도가 멈춘 것을 직접
  확인한 뒤에만 “실행 잠금 해제”를 누르고, 단계 이름을 입력하고 확인란을 체크해 “잠금 해제”합니다. 결과가 없으면 그 단계는 실패로
  기록되고 다시 실행하지 않습니다. 데스크톱에서 풀 수 없는 경우는 화면 안내대로 운영자가 CLI로 확인합니다.

절차와 주의점은 [학습 프로젝트·그래프 안내](TRAINING_WORKFLOWS.md)에 자세히 있습니다.

## 업데이트·제거

1. 앱의 컨트롤러 막대에서 **컨트롤러 정지**를 누르고 **정지 요청**을 고릅니다.
2. 상태가 **정지**가 될 때까지 기다립니다. 정지를 요청하면 새 단계는 시작하지 않지만 진행 중인 단계는 끝까지 돌므로,
   학습 중이면 몇 시간이 걸릴 수 있습니다.
3. 앱 창을 닫습니다.
4. 새 설치 파일(또는 Windows 설정의 앱 제거)을 실행합니다.

이유: 백그라운드 컨트롤러는 창을 닫아도 돌면서 앱 실행 파일과 학습 엔진(`factory-bridge.exe`)을 열어 둡니다. 설치 프로그램은
실행 중인 앱 창은 닫을 수 있지만, 컨트롤러가 진행 중인 단계를 끝낼 때까지 학습 엔진 파일을 바꿀 수 없습니다.

- 제거 창의 ‘애플리케이션 데이터 삭제하기’(영어 화면: ‘Delete the application data’)를 체크하면 앱 데이터 폴더의 프로젝트·데이터
  버전·실행 기록·설정이 모두 지워집니다. 의도한 경우에만 체크하세요. 제거만으로는 Windows 자격 증명 저장소의 인증값이 지워지지
  않으므로, 지우려면 제거하기 전에 연결 설정의 “저장된 인증값 삭제”를 누르세요.
- 0.3.0에서 업데이트하면 연결 설정과 저장한 인증값을 그대로 씁니다. 이전 작업 DB는 0.4.0이 처음 쓸 때 새 형식으로 바뀝니다.
- **0.4.0으로 연 뒤에는 0.3.0으로 되돌리지 마세요.** 바뀐 작업 DB는 0.3.0에서 다시 쓸 수 없습니다.
- 실행 중인 단일 학습 작업이 있으면 끝내고 결과를 회수한 뒤 업데이트하세요(아래 ‘실행 관리와 복구’).

## 학습(단일 학습)

1. **데이터**에서 JSON/JSONL 파일을 선택하고 ID와 버전을 지정합니다. Alpaca 또는 ShareGPT 형식이 필요합니다.
   등록 시 데이터 형식·해시를 검사하고 PC에 불변 사본을 보관합니다. GPU 전송 허용은 별도로 선택합니다.
   다른 데이터로 바꾸려면 새 버전을 등록합니다.
2. **학습 설정**에서 논문 추출·실험노트 생성·업무 분류 예제 또는 저장한 업무 설정을 선택합니다.
   업무 AI ID와 기반 모델은 별개입니다. 데이터 버전을 선택하고 기본 학습 옵션을 조정합니다.
   앱 기본값은 epoch 기준 학습이며, 예제 CLI의 2-step smoke 설정을 그대로 사용하지 않습니다.
3. 최신 모델은 **Hugging Face 모델 추가**에서 검색하거나 모델 ID를 입력해 확인·추가합니다.
   구조에 맞는 템플릿과 고정 commit을 적용하며 지원하지 않는 모델은 이유를 표시합니다.
   기본 목록에서 기반 모델을 바꾸면 **선택한 모델 버전 확인·고정**을 누릅니다. Hugging Face의 공개 메타데이터에서
   정확한 commit을 조회합니다. 모델 파일은 이 단계에서 내려받지 않습니다. 최초에는 공개 Qwen을 권장합니다.
   Llama 같은 접근 제한 모델은 이용 승인과 GPU에 준비한 캐시가 필요합니다. 연결 화면의 HF 읽기 토큰은
   메타데이터 조회용으로만 저장하며 GPU에는 전달하지 않습니다.
4. 업무 지표가 필요하면 **별도 검증 데이터**와 평가 방식을 선택합니다. 검증 데이터 없이 학습 완료만
   확인한 결과는 업무 품질 점수가 아닙니다. 학습 데이터와 검증 데이터가 중복되지 않도록 준비합니다. RM은 preference 검증 데이터와 reward 평가를 선택합니다.
5. **실행 계획 확인**에서 확정된 설정, 데이터, 최대 시간 기준 예상 GPU 비용을 확인합니다.
   기본 앱 정책은 GPU 1개·4시간·예상 비용 $5 이하입니다. 기존 Pod 전체 청구에 대한 강제 한도가 아닙니다.
6. **데이터 전송에 동의하고 학습 시작**을 눌러 실제 전송과 실행을 승인합니다.
   이후 데이터 전송 → LLaMA-Factory 학습 → 선택한 생성 평가 → 산출물 회수 → MLflow 저장을 실행합니다.
   기존 Pod는 끝나도 계속 과금될 수 있으므로 담당자가 상태를 확인하고 정지해야 합니다.

## 실행 관리와 복구

- **실행 관리**에서 상태, 회수된 학습 로그, 원격 실시간 로그와 평가 결과를 봅니다.
- **취소 요청**은 작업 취소를 요청하는 동작이며 원격 종료가 확인되었다는 뜻이 아닙니다.
  로컬 실행기가 연결을 잃었다면 Pod 또는 GPU 서버의 프로세스 상태를 확인해야 합니다.
- 앱 창을 닫아도 이미 시작된 원격 작업은 자체 시간 제한으로 실행됩니다.
  로컬 실행 프로세스도 살아 있으면 회수를 계속하지만 PC 종료 시에는 회수가 중단됩니다.
- 다시 앱을 열고 **연결 끊긴 작업 확인**, 해당 작업 선택, **재연결 · 결과 회수**를 사용합니다.
  마지막 heartbeat 이후 120초가 지나기 전에는 작업이 아직 실행 중으로 보일 수 있습니다.
  원격 작업이 끝나지 않았으면 나중에 회수를 다시 시도합니다. 불확실한 작업의 GPU 잠금은 유지합니다.
- 실제 취소와 체크포인트 회수·해시 검증 이후 체크포인트 이름을 지정해 재개할 수 있습니다.
  앱 버전을 변경하면 기존 명세의 소스 해시와 달라질 수 있으므로 실행 중에는 업데이트하지 마세요.

## 공용 기록 비교

**기록 비교**에서 실험 목록과 실행 기록을 조회하고 두 실행을 선택합니다.
50개씩 불러오며 다음 페이지를 추가할 수 있습니다. 설정과 지표를 나란히 표시하고, 동일 업무·검증 데이터
해시·평가 방식의 완료된 실제 실행에 한해 지표 차이를 계산합니다. 합성 데이터 표시는 유지합니다.
공용 MLflow의 접근 권한은 서버가 관리합니다. 기록 및 산출물에 포함할 수 없는 민감한 데이터는 넣지 마세요.

0.2.3에서는 불러온 기록의 검색·상태 필터, 변경된 설정 표시, 이전 설정으로 새 실험 준비를 제공합니다.
**이 설정으로 새 실험**은 설정만 불러오며 바로 실행하지 않습니다. 이 PC의 데이터 버전을 확인하세요.

## 새 화면과 미리보기

밝은 Linear·Vercel 계열의 작업 화면으로 개편했습니다. Ctrl+K로 페이지를 빠르게 찾을 수 있습니다.
데이터 등록 전에 **샘플 미리보기**로 형식·건수·중복 레코드와 앞 3건을 검사합니다. 미리보기는 32 MiB
이하 파일을 지원하고 긴 내용을 줄여 표시합니다. GPU 전송은 발생하지 않습니다.
학습과 검증에 byte 단위로 같은 스냅샷을 선택하면 실행 계획과 제출 단계에서 차단합니다.
부분 중복이나 의미상 유사한 데이터까지 탐지하는 기능은 아닙니다.

**실행 관리**의 저장된/원격 진행 지표는 LLaMA-Factory의 실제 trainer_log.jsonl을 읽습니다.
원격 지표를 선택하면 실행 관리 화면에서 10초 간격으로 갱신합니다. 손상·미완성 줄과 유한하지 않은
loss를 제외하며 최대 200개 지점을 표시합니다. 기록이 없으면 대기 상태를 보여 줍니다.
표시한 train loss는 업무 품질 점수가 아닙니다. 원격 조회에는 기존 Pod 또는 GPU 서버의 SSH 연결이 필요합니다.
유사 오픈소스 조사와 적용한 개선점은 [조사 기록](OPEN_SOURCE_REVIEW.md)에 정리했습니다.

## 저장 위치와 한계

- 설정·데이터 사본·작업 DB는 사용자 앱 데이터 폴더(`%APPDATA%\kr.kbiofoundry.tuningfactory`) 아래에 있습니다.
  이 폴더는 민감한 데이터를 포함할 수 있으므로 공유하거나 저장소에 올리지 않습니다. 설치 폴더를 바꿔도 같은 앱 데이터 폴더를 씁니다.
  - `executor-profiles.json`: 실행 프로필의 공개 항목(키 내용 없음)
  - `state/workflows/…`: 프로젝트·레시피(`workflow-revisions.sqlite3`), 기반 모델 설정·토크나이저와 모듈 구조, 평가 기준,
    계획(`plans/`), 계획 입력, 자원 확인 기록(`observations/`), 실행 등록 영수증(`submissions/`)
  - `state/registry/…`: 데이터 버전, 가져온 원본 사본, 분할 기록
  - `state/controller/…`: 백그라운드 컨트롤러 상태(`current.json`), 시작 실패 기록(`broker.json`), 정지 요청(`stop-request.json`).
    ID·해시·시각만 담고 인증값은 담지 않습니다.
  - `state/jobs.db`: 단일 작업과 그래프 실행의 작업 기록
- API 키·MLflow 인증값은 Windows 자격 증명 저장소에 있습니다. 실행 프로필의 RunPod API 키는 프로필마다
  `executor-profile/<프로필 ID>/RUNPOD_API_KEY` 항목에 따로 있습니다. 앱에서 저장된 인증값을 삭제할 수 있으며, 이때 실행 프로필의 키도
  함께 지워집니다. 일반 설정 JSON, 학습 명세와 Git에는 저장하지 않습니다.
- Pod 작업과 캐시는 /workspace/factory-desktop 아래에 생성합니다. 소스별 학습 환경을 분리합니다.
- GPU 서버 작업은 지정한 작업 폴더 아래에 생성합니다. 앱 소스 버전별 전용 환경(runtime), 작업 파일(jobs),
  모델 캐시(hf-cache), 내려받은 Python(python), uv 캐시(uv-cache)가 분리되며 pip는 캐시를 쓰지 않습니다. 선택한 GPU UUID만
  CUDA_VISIBLE_DEVICES로 지정합니다. SSH 개인키는 PC의 원래 위치에 남습니다. 서버 주소·포트·계정·지문·키 파일 경로·작업 폴더·
  선택 GPU·비용은 공개 설정으로 저장되지만 키 내용과 인증값은 저장되지 않습니다.
- GPU 서버는 서버당 공장 작업 하나만 실행합니다. RunPod Pod와 서버가 서로 다른 장비인지 증명할 수 없어
  교차 격리합니다. RunPod 작업의 GPU 잠금이 남아 있으면 SSH 작업·준비가 막히고, SSH 작업이나 SSH 준비 예약이 있으면 RunPod 작업과
  RunPod 환경 준비가 막힙니다. RunPod 환경 준비는 예약을 남기지 않으므로 SSH를 막지 않습니다. 같은 서버를 다른 주소로
  등록해도 우회되지 않습니다. 잠금은 이 PC의 로컬 상태에만 있어 다른 PC에서 쓰는 사용자는 막지 못합니다.
- 로그·진행·결과 회수는 작업을 시작한 서버·키·작업 폴더·선택 GPU에 묶입니다. 서버의 다른 GPU 구성이 바뀐
  것은 허용하지만 다른 서버나 설정으로 바꾸면 과거 작업을 이어받지 않습니다. 비용은 입력값 기준이며 실제 사용량 관측이나
  서버의 다른 사용자 작업은 확인하지 않습니다.
- 실제 SSH/BOP 서버·GPU·MLflow 서버·Hugging Face 머리글 조회 시험은 하지 않았습니다. 서버 기능은 가짜 SSH 응답으로 시험했습니다.
  설치본(WebView2 화면, Windows 자격 증명 저장소, 백그라운드 컨트롤러)은 개발 PC 한 대에서 GPU·네트워크 데이터 없이 검사했고
  결과는 [진행 기록](PROGRESS.md)과 [설치 검사 기록](acceptance/2026-10-22-desktop-040.json)에 있습니다. 한글 입력기 조합, 화면 읽기
  프로그램, 실행 중인 컨트롤러가 있을 때의 대화형 설치, 깨끗한 두 번째 PC와 코드 서명은 검증하지 않았습니다.
- 화면의 동작(목록 읽기, 저장, 계획 확인 등)은 매번 학습 엔진을 새로 시작하므로 개발 PC에서 한 번에 3~4초 걸립니다. 실행 상태를
  자동으로 다시 읽는 간격도 이 시간에 맞춰 늘어납니다.
- 백그라운드 컨트롤러의 알려진 한계(0.4.0):
  - 실행 자원에 연결한 뒤 원격 작업이 멈추는 경우를 감시하는 장치가 없습니다. “동작 중”인데 오래 진행이 없으면 컨트롤러를 다시 시작하세요.
  - 절전 뒤 다른 컨트롤러가 소유권을 넘겨받으면 이전 컨트롤러 프로세스는 진행 중이던 요청이 돌아올 때까지 남아 있다가 끝납니다.
  - MLflow가 처리 중으로 받은 모델 등록을 나중에 실패로 바꿔도 ‘등록됨’으로 보입니다.
  - 컨트롤러는 인증 환경 변수를 지우고 시작하지만 파일로 된 인증 정보(AWS 공유 인증 파일, Azure CLI 캐시, gcloud 기본 인증 등)는
    읽을 수 있습니다.
  - 리디렉션된 AppData에서는 컨트롤러를 시작할 수 없습니다(실제 리디렉션 환경에서는 시험하지 않았습니다).
  - 그래프 컨트롤러는 `MLFLOW_TRACKING_INSECURE_TLS`와 `MLFLOW_TRACKING_CLIENT_CERT_PATH`를 쓰지 않습니다. 자체 서명 인증서 서버는
    `MLFLOW_TRACKING_SERVER_CERT_PATH`로 지정하며, mTLS MLflow는 그래프 실행에서 지원하지 않습니다.
- 데이터·키 파일 경로 검사는 글자만 보므로 공유 폴더로 가는 링크·정션이나 네트워크 드라이브 문자는 알아채지 못합니다.
- ShareGPT 데이터는 새 화면에서 나눌 수 없고, 열 연결의 500개 선택 한도는 열 이름순으로 앞 500개입니다.
- 여러 PC 사이의 작업 대기열·GPU 잠금은 공유되지 않습니다. 사용자별 Pod 또는 지정 담당자가 필요합니다.
- 대량 데이터 스트리밍, 공통 GPU 배정, 무인 다중 Pod 운영, 서빙은 이번 버전에 포함하지 않습니다.
- PT·SFT·RM·PPO·DPO·KTO와 Full·Freeze·LoRA·QLoRA·OFT를 제공합니다. 단계별 데이터와
  옵션 조합을 검사하며 임의 모델/플러그인을 무조건 허용하지 않습니다. 검토한 텍스트 모델 15개 프로필이 범위입니다.
- S3는 endpoint·버킷·key를 직접 연결해 고정 사본을 PC에 가져옵니다(파일당 32 MiB).
  GPU의 직접 S3 인증이나 무제한 스트리밍은 제공하지 않습니다. S3 키는 Windows 자격 증명 저장소에 보관합니다.
- PPO는 별도 0.9.3 환경과 미리 준비한 보상 모델이 필요합니다. PPO·OFT 재개, Full/Freeze RM 재개,
  OFT의 별도 생성·보상 평가는 upstream 제약으로 차단합니다. PPO 프롬프트는 Alpaca 형식입니다.
- 새 조합은 CPU/UI·격리된 PPO import·로컬 S3 계약을 검사했으며 실제 GPU와 클라우드 S3 검증은 남아 있습니다.
- 실제 H100 + Qwen2.5-0.5B에서 LoRA·실제 4비트 QLoRA·생성·취소·체크포인트 10→100 재개·
  PC 실행기 강제 종료 후 결과 회수·MLflow 산출물 왕복 해시를 확인했습니다.
  다른 모델·대규모 데이터·새 PC 설치·코드 서명은 검증하지 않았습니다.
  [GPU 검증 보고서](GPU_ACCEPTANCE_2026-10-15.md)를 확인하세요.

## 실행 전 GPU 점검 (0.5.0)

학습 환경은 PyTorch 2.7.1 CUDA 12.8 빌드를 씁니다. 지원 GPU는 Ampere(A100·A4000·A6000·RTX 3090), Ada(L40S·RTX 4090),
Hopper(H100·H200), Blackwell(B200·RTX PRO 4000/6000)입니다. Turing(T4·RTX 20xx)은 세대 검사는 통과하지만 bf16이 없어 fp16을 써야 하고 검증 대상은 아닙니다. V100과 그 이전 세대는 거부합니다.

- **환경 확인**은 학습 환경과 함께 GPU 이름·세대(compute capability)·메모리·드라이버를 읽어 이 PC에 저장합니다.
  환경이 없으면 오류 대신 "학습 환경이 아직 없습니다"라고 알려 줍니다.
- **실행 계획 확인**은 네트워크를 쓰지 않고 저장된 GPU 정보로 미리 판정합니다. "실행 시 거부될 항목"과 "주의 항목"을
  나누어 보여 주며, 계획 단계에서는 제출을 막지 않습니다.
- **학습 시작·대기 작업 실행**은 승인 창을 띄우기 전에 GPU와 학습 환경을 다시 확인합니다(읽기 전용 SSH).
  거부 항목이 있으면 이유를 보여 주고 멈춥니다. RunPod Pod에 이 앱 버전의 학습 환경이 없으면 같은 승인 창에 설치 안내가
  함께 나오고, 한 번 승인으로 설치와 학습이 이어집니다(`/workspace/factory-desktop` 아래, 최대 30분, 수 GB).
  GPU 서버는 지금처럼 연결 설정에서 조회 결과를 검토한 뒤 "학습 환경 준비"를 먼저 눌러야 합니다.
- GPU가 없거나 사용 중이면 오류로 멈추며 학습 환경 준비를 제안하지 않습니다.
- 같은 GPU에서 다른 학습 환경 준비가 진행 중이면 "다른 학습 환경 준비가 이 GPU에서 진행 중입니다"라고 알리고 멈춥니다.
  끝난 뒤 다시 실행하세요.
- 실행 중 이 밖에 두 가지 거부가 나올 수 있습니다. 다른 작업이 Pod를 쓰는 경우 "다른 작업이 이 Pod를 사용 중이라 학습 환경을 준비할 수 없습니다. 실행 관리에서 그 작업을 재연결·결과 회수해 끝낸 뒤 다시 시도하세요.", 준비 직후 확인이 실패한 경우 "학습 환경을 준비했지만 확인을 통과하지 못했습니다. 연결 설정에서 '환경 확인'으로 상태를 확인하거나 '학습 환경 준비'를 다시 실행하세요."
- **거부**: 지원하지 않는 GPU 세대, 오래된 드라이버(525.60.13 미만), bf16을 지원하지 않는 GPU의 bf16 설정,
  작업 설정과 다른 GPU 종류·개수, 한도를 넘는 시간당 요금, 모델 가중치만으로 GPU 메모리를 넘는 경우.
- **주의**: CUDA 12.8 정식 드라이버(570.26) 미만, 빠듯한 예상 메모리, GPU에서 검증되지 않은 모델, 크기 정보가 없어 메모리를
  추정할 수 없는 모델("메모리 추정 불가"), 오래되었거나 없는 GPU 정보.
- 메모리 추정은 근사치입니다. 가중치·학습 상태·활성값(gradient checkpointing 가정)을 더해 계산하며, 실제 사용량은
  다를 수 있습니다. 작업 설정의 GPU 종류·요금은 연결 설정의 "GPU 정보 → 학습 설정에 적용"으로 맞출 수 있습니다.

  -it와 기본 모델)가 있습니다. 이 모델들은 비전·오디오 겸용 구조이지만 **텍스트 데이터만** 학습하며, 비전·오디오 부분은 항상 동결됩니다.
  A40(compute capability 8.6)에서 합성 데이터로 검증한 모델은 Qwen3.5-0.8B(SFT LoRA·QLoRA·full·freeze, DPO, PT, RM, 확정),
  Qwen3.5-9B(SFT LoRA), gemma-4-E2B-it(SFT LoRA, DPO, PT, RM)이며 목록에 'GPU 검증 이력'으로 표시됩니다. Base 모델과 다른 크기는
  아직 검증되지 않았고, 다른 GPU 세대에서는 검증 전이라는 주의가 나옵니다(결과는 [진행 기록](PROGRESS.md) 참고).
- **단계와 방법**: Qwen3.5와 Gemma 4는 SFT·DPO·RM·PT를 지원합니다. KTO는 현재 학습 엔진(LLaMA-Factory 0.9.5·transformers 5.6.0)에서 실패해(Qwen3.5는 멀티모달 위치 계산 오류, Gemma 4는 KL 배치의 멀티모달 입력 처리 오류) 지원하지 않습니다. PPO는 지원하지 않습니다.
  freeze 방식에서 Qwen3.5는 학습 모듈로 'Attention'과 'Attention + MLP'를 고를 수 없고, 입력·출력 임베딩을 공유하는 모델은
  'LM head'를 따로 학습할 수 없습니다.
- **Qwen3.5 템플릿**: 기본값은 `qwen3_5`(+`enable_thinking: false`)입니다. 일반 템플릿 `qwen3_5_nothink`로 학습하면 모델이 답마다 빈 `<think>` 블록을 스스로 생성하므로 기본으로 쓰지 않습니다. 카탈로그 모델의 저장된 설정은 템플릿 불일치로 거부되며('버전 확인'을 다시 누르세요), 이전에 등록한 모델 프로필이 이 템플릿을 가진 설정은 경고와 함께 검증됩니다.
- **추론 템플릿**: 추론형 템플릿(qwen3_5, qwen3_6, gemma4, gemma4n)에는 `enable_thinking: false`가 더해집니다. 허브에서 등록한
  `gemma4_text` 모델의 기존 작업도 이 설정이 바뀝니다.
- **메모리 추정**: 가중치는 비전·오디오를 포함한 전체 매개변수로, 학습 상태는 텍스트 매개변수로 계산합니다. QLoRA는 임베딩 표
  (Gemma 4 E 모델의 층별 임베딩 포함)와 MoE 전문가 가중치(Qwen3.5-35B-A3B, Gemma 4 26B-A4B)를 bf16으로 셉니다. bitsandbytes는 선형층만 양자화하고 전문가 가중치는 3차원 매개변수라 양자화하지 못하기 때문입니다. 어휘가 큰 이 모델들은 LM head 로짓(배치 × 최대 길이 × 어휘 × 11바이트, DPO·KTO 3배, full 2배)도 더하며, A40 실측 최대 메모리를 모두 덮도록 맞췄습니다([학습과 저장](TRAINING_AND_STORAGE.md) 참고). Hugging Face에서 등록한 모델도 크기 정보가 있으면 추정하고,
  기본 목록에 있는 모델을 허브로 등록하면 검토된 기본 목록 항목을 씁니다. 크기 정보가 없는 모델은 계획 단계에서
  "메모리 추정 불가" 주의가 나옵니다.
- **GPU 서버 요금**: 시간당 비용을 계획 단계에서 판정합니다. 작업 한도를 넘거나 비어 있으면 알리고 제출 전에 거부하며,
  0은 내부 서버로 허용합니다. GPU 서버 SSH 연결은 30초마다 keepalive를 보냅니다.
- **이전 학습 환경 정리**: 학습 환경 준비는 같은 작업 폴더에서 쓰지 않는 이전 앱 버전의 학습 환경을 지웁니다. 지운 환경의
  이름 목록과, 확보한 용량(볼륨 남은 공간의 차이이며 0.1GB 미만이면 용량 없이 개수만)을 준비가 끝난 뒤 보여 줍니다.
  한 번의 준비에서 정리에 쓰는 시간은 최대 300초이고 남은 것은 다음 준비 때 지웁니다. 같은 앱 버전의 작업이 그 환경을 쓰는 동안은
  "이 앱 버전의 학습 환경을 쓰는 작업이 실행 중이라 학습 환경을 다시 준비할 수 없습니다"라고 알리고 준비하지 않습니다.
  일부 환경을 지우지 못해도 준비에는 영향이 없습니다. 정리 뒤 설치 단계가 실패하면 정리 결과는 표시되지 않습니다.

## 업그레이드 시 주의

0.4.0(또는 다른 앱 버전)으로 제출된 작업은 0.5.0에서 실행할 수 없습니다. 앱은 접속하기 전에 이를 알리고 멈춥니다. 실행 관리에서 해당 작업을 **취소 요청**으로 정리한 뒤 학습 설정에서 다시 제출하세요.

RunPod와 GPU 서버는 같은 장비인지 증명할 수 없어 교차 격리합니다. 0.3.0에서 끝나지 않았거나 불확실한 RunPod 작업의 잠금이 남아 있으면
GPU 서버 작업·준비가 막히고 “다른 연결 대상(RunPod 등)의 끝나지 않은 작업 잠금이 남아 있어 GPU 서버를 사용할 수 없습니다. …”가 표시됩니다.
먼저 **실행 관리**에서 **재연결 · 결과 회수**를 시도하세요. 원래 프로세스와 Pod가 멈춘 것을 확인했고 회수가 불가능할 때만 앱 데이터 폴더의
state를 지정해 CLI로 잠금을 해제합니다(작업이 FAILED·CANCELED·COMPLETED이고 ATTEMPT_ID가 현재 시도일 때만 허용).

    uv run factory --state-dir "$env:APPDATA\kr.kbiofoundry.tuningfactory\state" status --job-id JOB_ID
    uv run factory --state-dir "$env:APPDATA\kr.kbiofoundry.tuningfactory\state" release-lock JOB_ID ATTEMPT_ID --confirm-execution-stopped

JOB_ID는 실행 관리 표의 업무 AI 이름 아래에 표시됩니다. ATTEMPT_ID는 표에 없으며 `status --job-id JOB_ID` 출력의 `active_attempt_id`에서 확인합니다.
설치형 앱에는 `factory` 명령이 들어 있지 않으므로 위 명령은 소스로 설치한 CLI에서 실행합니다(README의 ‘처음 설치하기’).
그래프 실행의 잠금은 **그래프 실행** 화면의 “실행 잠금 해제”로 풀 수 있습니다.
실제 학습 제출은 연습용 데이터(`tutorial_sample`)를 거부하며 “연습용 데이터(tutorial_sample)로는 실제 학습을 시작할 수 없습니다.”를 표시합니다.
재개는 원래 작업의 목적지를 먼저 확인한 뒤 작업 상태를 되돌립니다.

## 개발·빌드

개발 PC에는 Python 3.12, uv, Node.js, Rust 1.99.0, Windows C++ Build Tools와 WebView2가 필요합니다.

    uv sync --extra dev --extra tracking --locked
    uv run pytest
    uv run ruff check src tests scripts
    uv run python scripts/build_desktop.py
    cd desktop
    npm ci
    npm exec playwright install chromium
    npm test
    cargo test --manifest-path src-tauri/Cargo.toml --locked
    npm run tauri -- build --ci

빌드 결과는 desktop/src-tauri/target/release/bundle/nsis/에 있습니다.
UI 테스트는 가짜 연결을 사용하며 실제 서버·GPU 성공을 증명하지 않습니다.

설치 파일에 들어갈 학습 엔진(`dist/factory-bridge.exe`)은 `uv run python scripts/verify_desktop_package.py`로 검사합니다.
옵션은 다음과 같습니다.
- `--bridge PATH`: 검사할 엔진. 기본은 `dist/factory-bridge.exe`이며 설치한 앱 폴더의 `factory-bridge.exe`도 검사할 수 있습니다.
  `.py` 경로(`scripts/desktop_entry.py`)를 주면 빌드 없이 소스 상태의 엔진을 이 Python으로 실행하는 소스 모드가 되며, `wheel`을 뺀
  검사를 할 수 있습니다.
- `--check NAME`: `legacy`, `arguments`, `workflow`, `controller`, `wheel` 중 하나. 여러 번 줄 수 있으며 주지 않으면 모두 이 순서로 검사합니다.
- `--receipt PATH`: 출력한 JSON 결과를 파일로도 저장합니다.

결과의 `bridge_mode`는 빌드한 엔진이면 `frozen`, 소스 모드면 `source`입니다. 소스 모드에서는 빌드한 엔진만 보여 줄 수 있는 항목
(`frozen_engine`, `frozen_s3_sdk_loaded`, `frozen_lock_path`, `onefile_child_exited`)이 `null`이므로 설치 파일의 검사를 대신하지
않습니다. 소스 모드 검사는 자동 시험(`tests/test_verify_desktop_package.py`, Windows에서만)에도 들어 있습니다.

tests/native-smoke.mjs는 loopback WebView2 debugging을 켜고 실행한 앱에서만 수동 실행합니다. 앱은 PowerShell에서
`$env:WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS="--remote-debugging-port=9223"`를 설정한 뒤 실행하며, 스크립트는 `127.0.0.1:9223`에 붙습니다.
**스크립트는 이 PC의 실제 앱 상태에 씁니다.** 앱 데이터 폴더와 Windows 자격 증명 저장소 항목은 앱 식별자
(`kr.kbiofoundry.tuningfactory`)를 따르므로, 디버깅 포트를 켜고 실행한 앱도 평소와 같은 상태를 씁니다.
실행할 때마다 프로젝트(지울 수 없음)와 `desktop_smoke` 데이터가 남습니다. `FACTORY_SMOKE_FLOW=1`이면 데이터 버전, 레시피,
평가 기준과 모의 그래프 실행도 남습니다(그 전에 별도 명령으로 넣는 합성 기반 모델도 상태에 남습니다).
`FACTORY_SMOKE_LIVE_HF=1`이면 단일 학습의 모델 목록에 추가된 `Qwen/Qwen3.5-0.8B` 모델 프로필도 남습니다.
백그라운드 컨트롤러가 돌고 있거나 진행 중인 그래프 실행이 있으면 아무것도 쓰기 전에 멈춥니다.

기본 실행은 네트워크를 쓰지 않습니다. `FACTORY_SMOKE_LIVE_HF=1`이면 Hugging Face 메타데이터 조회를 함께 검사합니다(네트워크 사용).
저장된 인증값이나 실행 프로필이 있는 상태에서는 인증값 삭제 검사를 건너뜁니다. 실행 프로필, 저장된 인증값, MLflow 주소 중 하나라도
있으면 실제 컨트롤러를 시작하는 검사(프로필로 컨트롤러 시작·정지, 모의 그래프 실행)도 건너뜁니다.

`FACTORY_SMOKE_FLOW=1`이면 모의 그래프 실행을 백그라운드 컨트롤러로 끝까지 따라갑니다. 필요한 조건은 다음과 같습니다.
- 합성 기반 모델을 앱 상태에 먼저 넣어 둡니다(소스 저장소에서 실행).
  `uv run python scripts/seed_acceptance_root.py --state-dir "$env:APPDATA\kr.kbiofoundry.tuningfactory\state"`
- 실행 프로필이 없고, 저장된 인증값과 MLflow 주소도 없어야 합니다.
- 백그라운드 컨트롤러가 꺼져 있고 진행 중인 그래프 실행이 없어야 합니다.

일반 배포 앱은 디버깅 포트를 열지 않습니다. 실제 MLflow 읽기와 정지된 Pod 조회는
scripts/verify_desktop_readonly.py --connection-file ...로 별도 검증할 수 있으며 키를 출력하지 않습니다.
